# Memory Agent Workbench 未来目标与架构路线图

> 文档状态：未来方向主文档  
> 更新日期：2026-08-27  
> 适用范围：产品定位、底层架构、实施优先级与阶段验收  
> 参考原则：借鉴 dodo 的 Agent 内核、Hook、记忆、知识和 Skill/MCP 分层，但保持本地优先、模型可替换和独立实现。

## 〇、当前落地进展（2026-08-27）

已把「深层 Agent Runtime」落地为可替换的多后端 `server/runtimes.mjs`，工作台以「任务级黑盒」方式把整个任务交给本机 CLI 自主执行：

- **多后端注册表**：内置 `dsh`（DeepSeek Harness，`exec --profile headless`）与 `codex`（Codex CLI，`exec --sandbox`）两种后端，通过 `getRuntime`/`defaultBackend`（读 `AGENT_BACKEND` 环境变量，默认 `dsh`）切换；新增后端只需在 `RUNTIMES` 注册一个定义（入口发现 / spawn 参数 / 超时 / 摘要）。
- **统一语义**：共用 `normalizeSandbox`（`read-only` / `workspace-write`）、任务长度上限、进程 spawn、超时中止（SIGTERM + `*_TIMEOUT`）、输出上限截断与统一返回结构 `{ summary, data }`；错误码按后端前缀区分（`DSH_*` / `CODEX_*`）。
- **统一工具入口**：工具由 `dsh.run` 升级为 `agent.task`，输入含 `task` + 可选 `backend`（`dsh`/`codex`）+ `sandbox`，仍走现有「提交→待确认→批准→执行→审计」审批流，`permission: "write"` 默认需人工确认。
- **Work/Code 编排层**：`server/workagent.mjs` 封装双层 Agent——`CodeAgent`（`createCodeAgent`：校验 + 审批门 + 执行 + 审计，封装 runtimes 派发）作为底层执行器；`WorkAgent`（`createWorkAgent`：拉记忆上下文 → 模型决策 → 模型提出编码子任务时交给 `codeAgent.dispatch` 并把结果回喂继续推理，有界轮次）作为顶层编排器。只依赖注入能力，工作台可注入真实依赖、测试用假实现替换。
- **测试覆盖**：`server/runtimes.test.mjs`（默认后端 / 非法后端 / codex 执行与错误码）+ `server/workagent.test.mjs`（审批门、work→code 派发与回喂、有界轮次）+ 沿用 `server/dsh.test.mjs`，全套 264 用例绿。

> 待办：在本机真正安装 `@openai/codex` 后做一次 codex 端到端实测；DSH 真实链路仍有工作区权限（`EPERM`）排障待收尾。

## 一、目标定位

Memory Agent Workbench 的长期目标不是继续扩充一个聊天客户端，而是成为一个**本地优先、权限受控、过程可审计、模型可替换的桌面 Agent 工作台**。

对话只是任务入口。完整产品闭环应当是：

```text
理解目标
  -> 制定计划
  -> 获取记忆与知识
  -> 选择并调用工具
  -> 对高风险操作请求确认
  -> 执行并验证结果
  -> 交付可检查的产物
  -> 提议沉淀长期记忆
```

产品首先服务单用户、本地桌面场景。云端多租户、组织权限和大规模分布式调度不作为近期前提。

## 二、未来最重要的方向

项目后续按以下顺序投入，前一层未形成可靠闭环时，不用后一层的功能数量掩盖底层缺口。

### 1. Agent Runtime：从单轮聊天升级为有界任务循环

建立与模型供应商无关的 `AgentRuntime`，统一承载规划、模型调用、工具提议、结果观察、继续推理、停止和取消。

重点包括：

- 支持有最大步数、最大耗时、上下文预算和取消信号的多步骤循环。
- 模型只能提议工具调用，不能绕过工具注册表直接产生外部副作用。
- 每一步都保存输入摘要、模型决策、工具结果、耗时、错误和产物引用。
- Codex、OpenAI-compatible、Anthropic、DeepSeek 作为可替换 Runtime/Model Adapter，不把产品绑定在单一 CLI 或模型上。
- 先把单 Agent 任务闭环做可靠，再引入专家团和多 Agent 调度。

建议的 Runtime 事件协议：

```text
task.created
prompt.submitted
context.loaded
model.started
model.delta
tool.proposed
tool.approval_requested
tool.started
tool.completed
tool.failed
artifact.created
memory.proposed
task.completed
task.failed
task.cancelled
```

### 2. Hook 与事件控制面：让每次执行都可拦截、可观察

现有任务、审批和审计能力应升级为统一事件控制面，而不是继续在各 API 路由内增加特例。

- Pre Hook：参数校验、权限判断、路径边界、用户确认和策略拦截。
- Post Hook：结果归一化、产物登记、审计记录、失败恢复和后续步骤判断。
- Stop Hook：刷新待写数据、等待后台任务、生成任务总结并安全关闭。
- Hook 只负责策略和事件，不承载具体业务实现。
- 事件格式必须版本化，便于桌面端、插件和未来 Runtime 共同消费。

### 3. 权限、安全与沙箱：自治能力必须建立在控制面之上

安全性优先于自动化程度。

- `read` 工具可以在受限范围内自动执行。
- `write`、`external`、`publish`、`delete` 等操作默认需要明确确认。
- 所有文件操作限制在已授权工作区，继续防止绝对路径、路径穿越和符号链接逃逸。
- Codex 或其他 Agent Runtime 默认只读；不得使用自动审批参数绕过工作台的权限层。
- Bash、第三方 Skill 和未知 MCP 工具进入隔离进程，配置超时、输出上限和可终止机制。
- API Key、Token、密码、私钥和订阅地址不得写入对话日志、长期记忆、审计正文或 Git。
- 提示词负责行为引导，代码层权限才是最终强制边界。

### 4. 记忆与知识分层：分别解决“以前”和“现在”

长期记忆与任务知识继续保持独立，禁止混成一个无限增长的 Prompt。

#### 长期记忆

- 保存用户偏好、稳定事实、历史决策和可复用经验。
- 保持“候选 -> 审核 -> 生效”的先审后写流程。
- 自动检索提供少量基础上下文，Agent 可按需主动深度检索。
- 所有记忆可查看、编辑、禁用、删除和追溯来源。

#### 知识系统

- 保存项目文件、文档、代码仓库、网页资料和外部平台数据。
- 每个知识源记录来源、获取时间、可信级别、可写性和刷新策略。
- 知识默认按需获取，不自动把大体量内容塞入上下文。
- 回答引用知识时保留文件、页面或外部来源证据。
- 易变知识必须检查新鲜度；过期时主动刷新或明确提示。

一句话边界：**记忆回答“用户是谁、以前怎么做”，知识回答“当前任务是什么、现在的数据是什么”。**

### 5. Skill 与 MCP：形成可扩展但不失控的能力体系

- 建立统一 `SkillManifest`：标识、版本、说明、触发条件、入口、权限、依赖和兼容性。
- Skill 通过清单发现，禁止运行时无边界扫描和直接执行未知脚本。
- Skill 指令与执行代码分离；`SKILL.md` 负责使用契约，执行器负责真实副作用。
- MCP Server 统一经过配置、启停、健康检查、工具发现和权限映射。
- MCP 工具进入现有工具注册表，继续继承审批、任务状态、审计和结果大小限制。
- 第三方能力默认不可信，安装、升级和新增权限必须由用户确认。

### 6. 本地数据底座：从文件集合演进为可迁移的数据系统

短期继续兼容现有 JSON/Markdown 数据，逐步把 SQLite 设为权威数据源：

```text
SQLite
├── conversations / messages
├── tasks / task_steps / hook_events
├── memories / memory_candidates
├── knowledge_sources / knowledge_chunks
├── skill_registry / mcp_servers
├── artifacts
└── audit_logs
```

- Markdown 保留为人工可读导出和审计摘要，不再承担并发主数据库职责。
- Embedding、全文索引和派生摘要必须可以从权威数据重建。
- 每次数据结构变化都要有 schema 版本、迁移脚本、备份和失败回滚策略。
- 提供全量数据导出、恢复校验和版本兼容测试。

### 7. 桌面产品化：让架构真正成为可安装的软件

- Electron 主进程统一管理单实例、窗口、本地服务、动态端口、子进程和退出收尾。
- Codex Bridge 等本地依赖由应用负责启动、检查、重启和关闭，不能要求普通用户另开终端。
- API Key 优先保存到系统 Keychain，数据继续保存在用户应用目录。
- 建立应用图标、版本号、升级迁移、崩溃恢复和诊断日志。
- 本机测试包与公开分发包分开验收；公开发布需要签名、Hardened Runtime、公证和 Gatekeeper 验证。
- macOS 稳定后再验证 Windows/Linux，不以配置里存在 target 代替真实跨平台验收。

### 8. 专家团与多 Agent：最后扩展，不抢占底座建设

专家团是单 Agent Runtime 的上层编排，不是另一套执行系统。

- 一个任务只有一个明确的 Orchestrator/Lead 负责状态推进和最终交付。
- Member 通过相同的任务、工具、权限、事件和审计协议工作。
- 并行执行必须有依赖图、预算、取消、冲突处理和结果汇总。
- 单 Agent 尚不能可靠调用工具并验证结果时，不进入真实多 Agent 自动调度。

## 三、不可破坏的架构原则

以下约束优先级高于功能开发速度：

1. 模型不直接拥有副作用权限，副作用只能由受控工具执行。
2. 只读可以自动，写入、发布、删除和外部发送必须可确认。
3. 工具结果属于任务证据，不能未经审核自动升级为长期记忆。
4. 记忆、知识、会话、任务、工具结果和产物分层存储。
5. 所有长任务都必须可取消、可超时、可恢复、可解释当前状态。
6. 所有外部内容都按不可信输入处理，不能覆盖系统安全规则。
7. 本地优先主流程在没有云服务、没有 API Key 时仍应保留可用能力。
8. 测试和构建通过不等于产品验收；还要验证真实桌面启动、权限交互、数据恢复和视觉流程。

## 四、明确的非目标

近期不做：

- 不复刻 dodo 的品牌、百度内网依赖、远程持久层和临时容器实现。
- 不为了“全自动”取消人工审批、安全边界和结果验证。
- 不优先建设云端多租户、组织权限、计费和大规模集群调度。
- 不先堆积大量 Skill、MCP Server 或模型供应商，再补 Runtime 和权限协议。
- 不把角色提示词或安全提示词当成真正的权限系统。
- 不把 UI 相似度、动画或视觉包装作为 Agent 闭环完成的证明。

## 五、阶段路线图

### M0：协议冻结与现状收口

目标：先确定后续代码都要遵守的契约。

- 定义 `AgentRuntime`、`AgentEvent`、`ToolCall`、`ApprovalRequest`、`Artifact` 接口。
- 盘点现有 chat、tool、task、memory、audit 接口并建立迁移映射。
- 修复 Electron 开发启动、端口、单实例和退出生命周期问题。
- 为现有能力建立桌面端基线验收。

完成标准：新功能不再绕过统一任务、权限和事件协议。

### M1：单 Agent 有界执行闭环

目标：让模型可以真正完成“思考 -> 调工具 -> 看结果 -> 继续 -> 交付”。

- 完成多步骤 Agent 循环、预算、超时、取消和最大步数。
- read 工具自动执行，write/external 工具暂停并等待确认。
- 工具失败可反馈给模型进行有限重试或调整计划。
- 最终响应包含结果、证据和产物引用。

完成标准：至少用三个真实任务验证读取、写入审批、失败恢复和取消。

### M2：统一 Hook、审计与恢复

目标：所有 Runtime 和工具共享同一控制面。

- 实现版本化事件总线和 Pre/Post/Stop Hook。
- 任务重启恢复、后台任务刷新和异常退出标记。
- 审计记录不包含正文、密钥和敏感参数，只保存必要元数据和摘要。

完成标准：任一任务都能回答“谁在何时请求了什么、是否确认、执行结果如何”。

### M3：知识系统与数据迁移

目标：把项目上下文从临时文件集合升级为可管理知识源。

- 定义 Knowledge Source、Chunk、Citation 和 Freshness。
- 建立文件导入、分块、全文检索和引用。
- 设计 SQLite schema 与 JSON/Markdown 迁移、备份和回滚。

完成标准：回答可以引用具体知识证据，旧数据可无损迁移并恢复。

### M4：Skill、MCP 与隔离执行

目标：安全扩充能力，而不是继续把工具写死在主服务中。

- Skill Manifest、发现、启停、版本和权限展示。
- MCP Server 生命周期管理和工具映射。
- 第三方执行器进程隔离、超时、取消和输出限制。

完成标准：安装或启用一个扩展前能明确看到它需要的权限；执行后有完整任务记录。

### M5：桌面交付与公开发布准备

目标：普通用户无需终端即可安装和运行。

- 内置服务和 Bridge 生命周期闭环。
- Keychain、数据迁移、备份恢复、诊断与崩溃恢复。
- macOS 签名、公证、安装包和升级验证。

完成标准：在干净用户环境完成安装、首次启动、模型配置、任务执行、重启恢复和卸载保留/清除数据验证。

### M6：专家团真实调度

目标：在同一 Runtime 协议之上引入 Lead/Member 协作。

- DAG 依赖、并发预算、共享证据、冲突处理和统一交付。
- 每个 Member 的工具权限、步骤和产物可独立审计。

完成标准：多 Agent 相比单 Agent 在指定复杂任务上产生可测量收益，而不是只增加调用次数。

## 六、近期执行顺序

下一轮开发建议严格按以下顺序推进：

1. 写出 `AgentRuntime` 和事件协议 ADR。
2. 把聊天接口与工具接口接入同一 Task 状态机。
3. 完成一个最小多步骤 Agent 循环。
4. 增加统一 Pre/Post/Stop Hook。
5. 修复 Electron 生命周期并接管 Codex Bridge。
6. 再开始知识系统和 SQLite 迁移。

在第 1 至第 5 项完成前，不把新增模型、更多办公工具、更多专家团角色或视觉改版列为最高优先级。
