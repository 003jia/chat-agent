# 失败用例分层诊断与修复手册

> 使用方式：先按 `{{TEST_FRAMEWORK}}` 报告定位失败，再严格按 L1→L5 排查。读完对应章节后再修改用例，不要为“让测试通过”直接放宽断言。

## 诊断总表

| 层级 | 类别 | 典型现象 | 先做什么 |
|---|---|---|---|
| L1 | 环境/网络 | DNS、连接超时、代理 403、全局 5xx | 直连/代理对比，探活 `{{HEALTH_ENDPOINT}}` |
| L2 | 账号/权限/数据状态 | 401/403、资源池不足、账号状态不满足 | 查询账号、角色、租户和资源状态 |
| L3 | 业务逻辑 | 字段值、权限边界、状态流转不符 | 对照最新文档、源码和可复现请求 |
| L4 | 数据假设 | 共享环境残留、空列表假设失败 | 查看写入日志，核实真实数据集 |
| L5 | 代码/技术 | import、路径、参数、解析、fixture 错误 | 最后检查测试和客户端代码 |

黄金法则：未排完 L1-L4，不要直接修改测试断言或业务代码。

## L1：环境与网络

检查：

- Base URL、环境变量、代理和 `no_proxy` 是否正确。
- 服务健康检查和 DNS/端口是否可达。
- 直连与代理结果是否不同。
- CI 与本地的网络、证书、超时配置是否不同。

环境问题应修复配置/运行环境，不能把接口失败改成 `skip` 或吞异常，除非该项目明确规定此类前置降级。

## L2：账号、权限与数据状态

检查：

- Token/Cookie 是否存在、过期或属于错误环境。
- 当前账号角色、租户、部门和资源授权是否符合用例前置。
- 账号是否为受保护预置账号；不要为了测试修改它。
- License/配额/资源池是否耗尽。
- 需要多个资源时，先动态查询数量。

权限测试应验证“允许”和“拒绝”两个方向；状态不满足且不能安全恢复时，明确 `skip`，不要改成两种结果均可。

## L3：业务逻辑

逐项核对：

1. 接口文档的 Method、Path、参数名和响应结构。
2. Controller/Handler → Service → DAO/外部依赖的实际逻辑。
3. 状态流转、枚举大小写、空值语义、幂等和错误码。
4. 当前环境是否有显式差异。

复现请求后，只修改与证据一致的断言；不以 HAR、历史响应或前端类型定义单独作为最终依据。

## L4：数据假设

常见问题是共享租户并不为空、其他用例残留、列表顺序不稳定、固定 ID 已被删除。修复方式：

- 用查询接口确认实际数据。
- 自行构造并清理测试数据。
- 用唯一字段定位目标，避免固定下标。
- 把“空数据时行为”与“有数据时行为”分开测试。

## L5：代码与技术

检查：

- import 和项目实际目录。
- fixture 名称、作用域和资源关闭。
- 参数类型、请求编码和文件路径。
- 响应嵌套取值路径。
- 日志、报告和临时目录是否正确。

## 修复三禁

禁止：

1. 为通过测试删除必查断言或把精确断言改成“非空即可”。
2. `except AssertionError: pass` 或吞掉接口异常。
3. 把产品 bug 改成允许的业务结果，或把多个互相矛盾的结果写进同一个成功断言。

修复完成后必须：

- 先单跑修复用例；
- 再跑整个模块；
- 至少重复运行 `{{REPEAT_COUNT}}` 次确认无数据污染；
- 记录根因层级、证据、改动文件和剩余风险。

## 缺陷判定

排除 L1/L2、测试代码和文档误读后，若源码实现与产品/接口契约不一致，按 `{{BUG_PLATFORM}}` 提交缺陷，保留原始失败断言和复现信息，不写死 `skip`。
